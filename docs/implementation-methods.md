## 2. 离线运行：结构化动作 → 校验 → 回放日志

现有代码先接收结构化观察，而不是从游戏截图自动识别状态。观察声明包含
`run_id`、`observation_id`、`screen`、`available_options`、
`captured_at_ms` 和 `source`。

当前动作示例是：

```json
{"run_id":"run_1","observation_id":"obs_42","kind":"select","option_id":"route_left"}
```

它表达“选择当前观察里的这个选项”，不是任意点击坐标或一段可执行代码。
[动作校验器](../src/arknights_vision_agent/actions.py) 按以下顺序检查：

1. 严格解析 JSON，拒绝重复字段等不合法输入；动作文本上限为 16384 字节。
2. 只接受 `select`、`wait`、`stop` 各自规定的字段、类型和标识符。
3. 核对动作与观察属于同一局、同一次观察。
4. `select` 仅用于招募、路线、事件页面，选项必须确实列在当前观察声明里。
5. 非 `stop` 动作拒绝未来或过期观察；默认有效期为 5000 毫秒，可配置。
   `wait_ms` 必须是 1–10000 的整数；终止状态只能接受 `stop`。

这些检查不证明上游提供的选项或页面识别正确。今后的真实控制器还需要把
选项映射到经过确认的截图区域，并验证屏幕没有过期或发生坐标变换。

[回放器](../src/arknights_vision_agent/replay.py) 校验预先给定的完整轨迹，
再按顺序处理动作；第一个错误或 `stop` 就结束。它输出
`allowed_dry_run`、`blocked` 或 `stopped` 事件。
[命令行](../src/arknights_vision_agent/cli.py) 将事件逐条写入
`events.jsonl`，将统计写入 `summary.json`，并拒绝复用已有输出目录。

所有回放事件都保留 `executed=false`，汇总保留 `game_clear_verified=false`。
回放不会真实等待、调用模型或控制设备；改一个动作也不会产生另一个游戏未来。
`stop` 只是结束代理/回放，不是暂停游戏、撤退或放弃肉鸽。

## 3. 数据准备：声明检查、整组划分、字节盘点分开做

### 3.1 检查清单声明

[清单校验器](../src/arknights_vision_agent/demonstrations.py) 接受
1–10000 条记录，保存本局/录像/分组身份、观察、动作、媒体时间范围、
操作开始时间、标注来源、审核状态与使用许可声明。

当前 v1 只检查填写的固定时钟偏移是否自洽：

```text
media.end_ms + media.media_to_run_offset_ms = observation.captured_at_ms
observation.captured_at_ms <= decision_at_ms
```

还要求映射后的起点非负、图片是单一时间点、同一局或录像的来源/分组一致、
同一局—录像对的偏移一致。唯一性要求是 `record_id` 在清单内唯一，以及
`(run_id, observation_id)` 组合唯一；`run_id`、`recording_id` 和
`leakage_group_id` 可以跨记录复用，以关联同局、同录像或同组的样本。
它不读取视频来求出偏移，也不能证明被引用的视频真的只含所声明时间范围内的画面。

标注来源 `input_log`、`human`、`inferred` 始终保留，审核状态为
`pending`、`accepted`、`rejected`。推断标签经过人工接受后仍是推断标签，
不会变成原始操作日志。声明有审核编号或使用许可也不等于系统验证了这些证据。

### 3.2 标出候选资格，并按整局相关组划分

[准备报告](../src/arknights_vision_agent/preparation.py) 将真实录制来源、
标签已接受、使用许可声明为真的记录标为 `metadata_eligible`；合成、待审、
拒绝或未获使用许可的全部排除原因都会保留。这个字段不是“可直接训练”认证。

分区以 `leakage_group_id` 为单位：同一局及相关录制版本应被声明成同一组，
然后整组分配到训练、验证或测试分区。当前算法是：

```text
payload = 固定版本前缀 + 规范 JSON([seed, leakage_group_id])
bucket = SHA-256(payload) 作为大端整数取模 10000
默认：0..7999 → train；8000..8999 → validation；9000..9999 → test
```

固定配置下，行序、其他组的增加或标签资格变化不会改变该组分区。默认权重
为 8:1:1，但不保证小样本的实际数量恰好符合这个比例；不合格记录也会获得
分区，报告分别统计“已分配”和“满足声明资格”的数量。关联组仍需正确填写，
算法不会自动识别所有相似视频或隐藏的跨组关联。

另一个摘要对按 `record_id` 排序的规范化清单加版本前缀后计算 SHA-256，
用于辨认声明版本。它不是所引用媒体文件的内容哈希。

### 3.3 读取明确选定的文件，计算内容指纹

[文件盘点器](../src/arknights_vision_agent/inventory.py) 才会读取文件字节。
它只处理请求中明确列出的本地普通文件，限制数量和读取字节，在所要求的
POSIX 文件描述符路径上拒绝下级符号链接和非普通文件，并检查观测到的
读取前后文件变化。该操作不提供对恶意并发修改的不可变快照保证。

它以 `(文件字节数, SHA-256)` 给出完全重复候选，不删除文件、不解码视频、
不判断视频视觉相似度，也不把文件自动转成训练样本。当前已验收输入是合成
素材；真实录像仍需要 H02/H03 的私有样本与审核。

## 4. 视频处理：已做的实验与尚待实现的方法

### 已做的窄范围实验

[实验回执](media-runtime-calibration.md) 保存了本机 CPU 构建和一个
160×90、12 帧 H.264 MP4 的实际测量。检查的是实际返回的整数 PTS 和
`1/1000` 时基，帧间隔为 40/60 毫秒；缺失的帧 DTS 保持缺失，不用平均帧率
补造时间。这是一次合成短片测量，不是完整视频索引、抽帧产品或训练数据集。

### 拟议的后续流水线，尚未实现

1. **逐帧时间索引。** 对明确选定且身份已核对的文件，使用已固定和验证的
   解码器，在受限子进程中读取帧信息。保留原始整数时间戳、有理数时基、
   缺失值、帧序号、尺寸、裁剪和方向信息；呈现时间按 PTS × 时基计算，
   不用平均帧率猜每帧时间。调用参数、限制与数据接口还需要完整规范和验收。
2. **测量时钟对应关系。** 将录像时间与操作日志时钟对齐，记录偏移、可能的
   漂移和不确定性。当前 v1 毫秒偏移字段只是声明检查，并不会自动做这一步；
   有理数时间或漂移不能未经设计就四舍五入塞进现有格式。
3. **只选决策前的可见画面。** 若操作发生在对齐后的 10.0 秒，10.2 秒的
   操作结果画面不能作为这次决策的输入。即使某帧标为 9.8 秒，也要核对实际
   帧身份和对齐误差，不能仅凭一个请求的定位时间认定它合格。
4. **验证实际抽出的帧。** 记录返回帧的时间、尺寸、内容指纹及像素空间变换。
   保留旋转、裁剪、缩放关系，后续才有依据把画面区域映射到控制器坐标。
   当前实验没有完成这些几何、异常素材或时间边界的验证。
5. **生成并审核观察—动作样本。** 组合决策前的短帧序列、当时可用的状态/
   历史和有来源的动作标签。结果和失败信息单独保存，不能把操作后的结果
   画面混进该次策略输入。无操作日志的视频只能先产生候选推断标注，再审核。
6. **按整组划分、导出并离线验收。** 补齐真实媒体、标签和时钟验证，再单独
   设计样本导出与评测；不能把现有 `metadata_eligible` 当成全部工作已完成。

先前的 [视频索引提案](native-index-proposal.md) 保留了具体技术风险。
H08 尚未确认；索引、抽帧、样本投影各自需要规范与测试，实际训练仍留到后期。

## 5. 为什么现在先处理 MAA/控制器

这是用户在 2026-09-08 明确调整的优先级。具体比较与固定源码依据保存在
[控制器优先研究记录](controller-first-notes.md)。接入现成 MAA 自动化作为基线、
建立自研策略的底层控制接口、训练模型自主决策，是不同的交付物。
真实控制仍需先确定游戏平台和指定设备，依次验证截图、经批准的单次输入、
新画面中的实际效果，再推进监督下的战斗与有限整局测试。

任何现成自动化结果都要单独归因。控制器日志可以帮助后续数据采集，但本项目
提交的输入日志、第三方自动化内部的全部操作和游戏实际效果并不是同一份证据。
不要预先承诺能从 MAA 的任务回调还原全部逐次操作。
